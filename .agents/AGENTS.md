

- **Matrix API Reference**: Before adding a new method to `matrix` or `matrix.h`, check `.agents/MatrixAPI.md` — a full map of every constructor/factory/method already on `matrix`, grouped by category (shape ops, reductions, arithmetic, linear algebra, autodiff/JIT, refcounting, etc). Avoids duplicating existing functionality.
- **Memory Architecture (read before touching memory)**: Before editing anything in `primitives.cpp`, any `matrix` constructor/destructor/assignment, or `releaseBuffer`/`releaseTape`/`update_cache`/`update_from_trace`/`shareBuffer`, you MUST read `.agents/MemoryManagement.md`. It covers the two refcounts (instance vs buffer), the compile/execute rule (EXECUTE never allocates), the CPU -> Metal rerun guard every owning primitive needs, and the laws for transient (view) primitives. The model is manual on purpose, for performance: nothing enforces these rules at compile time.
- **Creating New Operations**: When asked to add a new primitive or operation to the compute graph, you MUST read `.agents/AddingNewOps.md` to understand the 5-step pipeline for frontend building, dimension collapsing, and CPU/Metal multidimensional dispatching.
- **Testing Standard**: All new mathematical ops must be verified against an exact Python equivalent using `mlx.core` (saved as a temporary `test_mlx_{op}.py`), and tested inside the `computational_graphV2` function in `MatrixH.mm`. You MUST delete the python test script after verification to avoid polluting the workspace.
- **Rendering Architecture**: For the `GeoNode`/`Viewer`/`Controllers` scene-graph and render-loop pattern (the current, modern approach — model new rendering code on this), see `.agents/Rendering_3D.md`. For the two superseded systems it replaced (`Shape<T>` and `GeometryNode<T>`, still physically present in `MatrixH.mm`/`Mods/GeometryNode.mm` and still drawn by the legacy `Renderer` path), see `.agents/Legacy_Rendering.md` — do not model new code on those.
- **Applets and the control panel**: Every `Intelligence` method is a self-contained applet started from `onAppear` in `3D_Editor.swift`. Before writing or changing one, read `.agents/Applets.md`: the parameters-are-leaves philosophy, `SliderGroup` (`UI/MatrixSliders.h`: `section`, `slider`, `slider_int`, `toggle`, `button`, `set`, `on_change`, `run_graph_pass`), the native `AppletPanel` (`UI/AppletPanel.h/.mm`, AppKit + UIKit, shown by the `ControlPanel` representable), the iOS floating/docked panel modes and the renderer's touch shield, the renderer hand-off controllers, and a catalogue of the applets. `UIComponent`/`components` are legacy (not displayed): don't use them in new code. Generator parameters become slider-drivable through `ScalarArg` (`.agents/Generators.md` §6); non-graph algorithms through `matrix::host_op`.
- **Threading (read before sharing a graph or buffer across threads)**: `.agents/Concurrency.md`. One owner thread per graph writes its leaves and runs its passes; other threads send writes to it (`dispatch_async`) and receive plain tapeless snapshots. A version bump is a recompute signal, not a publish. It also covers why the older applets never raced, pass IDs from `++global_epoch`, the designed-but-unbuilt `ThreadBarrierPrimitive` / mailbox leaf, and the known GPU in-flight buffer gap.
- **LiDAR mapping project (PS 26053)**: `.agents/LidarMapping.md` covers the brief, the pipeline (`AI/Kitti.h` → `AI/RangeProjection.h` → `AI/SalsaNext.h` (MLX, macOS only) → `AI/FoveatedGrid.h`), the SalsaNext conversion and port, SemanticKITTI data and the partial-download script, the 2.5D grid's design, the measured results, phone LiDAR vs the model, `CapReader`'s depth-vs-disparity fix, and the tests/tools in `tools/salsanext/`. Python tooling uses `/opt/miniconda3/bin/python` (torch + mlx).
